# 导入恢复与完整本地原包验收（第二十三批）

本批收口插件导入的恢复交互，并用完整本地原包扩大真实业务验证。最终证据入口为 `output/legacy-node-2026-10-16/plugin-import-original-delivery-verification.json`。整体目标仍为 active，不能据此宣称多数 ZTools 插件已经可用。

## 导入交互

- 原生选择框出现前即锁定扫描、选择、导入、启用及打开动作，防止重复写入。离开页面只忽略迟到的 UI 响应，不冒充取消已经开始的原生导入。
- 只有可导入候选默认勾选；扫描失败保留上一份候选和选择。
- 本次导入使用来源路径快照。部分成功后，移除已尝试路径，只把报告中明确失败的原路径重新加入选择；不从经过清洗的插件 ID 反推来源。
- 成功报告与读取插件列表的结果分开保存。读取失败提供独立重读，不重复导入。
- 后端返回停用插件时，明确提供“启用并打开”。启用成功、读取失败后只重读状态；确认真实启用记录后，经原 PluginOpenController 与 App 激活握手打开。
- 结果行优先显示已读取的清单标题，保留 ID；状态和动作处于同一布局单元，窄屏可换行。

真实 App 的静态 Chromium 验收为 `output/import-transaction-browser-2026-10-16/e3e80d73-a3ad-4001-b769-f2e6a6c7d40e/report.json`。包含 800×600、420×560 的浅深色八张截图，Root 均实际查看。关键结果态检查操作与状态可见、无横向溢出，覆盖部分成功、独立重读、仅重试失败源、只启用一次及离开后的迟到扫描。这里的 IPC、候选、选择框和激活失败均为合成数据，不是原生选择框或真实安装流程的验收。

## 内联模块资源修复

真实原包验收发现：内容整理工坊的 HTML 已显示，但 inline module 的相对依赖加载失败，按钮尚未绑定处理逻辑。宿主现将本地静态 import、export-from 和引号字符串形式的动态 import 指向现有插件资源会话。外部模块与改写后的内联依赖共用该 Panel 的一个惰性会话，关闭时回收。

路径仍按入口文件或已声明的本地 base 解析，保留 query/hash，复用现有插件目录边界。原文件保持原字节；不改 CSP、opaque sandbox，不增加 Node、网络或 LLM 依赖。

新职责分为 `pluginInlineModules.ts` 的依赖改写与 `pluginHtmlScripts.ts` 的活动脚本定位。后者跳过注释、template 和 rawtext 中的脚本示例，不使用 DOMParser、不重新序列化文档、不加载资源。词法分析新增能力为 opt-in；默认 preload 分析仍保持原输出契约。

预算在词法解析前检查：每个被扫描的 inline module 至多 256 KiB UTF-8，同页累计至多 2 MiB（包含没有本地 import 的模块），本地依赖引用总数至多 128（重复引用照计）。相同 specifier 复用解析 Promise；替换采用一次分段拼接，校验范围及重叠。以上是这条准备路径的工作预算，不是整个进程的内存上限。

裸包名、远端地址、计算得到的动态 specifier、动态 import options 及完整 import.meta 语义没有新增支持声明。这里只验证已注册样本与明确覆盖的语法。
