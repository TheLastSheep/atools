# Task13 main-owned background startup contract

Overall objective remains complete ZTools capability parity, unchanged Harris originals first. Previous goal turn was progress: Task12 changed production lifecycle behavior and independently passed 620 related tests. Task13 completes actual registration/startup/session reuse; a registry flag alone is not completion. GUI/App/AppleScript/native probes remain deferred. No dependency install, original-package edits, app replacement or Git mutations.

## Registration and authority

Original Electron `ipcRenderer.invoke("ztools:db-get", "auto-start-plugin")` and `db-put` with that exact key map only to the current plugin's requested startup preference. No arbitrary global DB keys or foreign plugin writes. Backend derives canonical plugin name from installed manifest; get returns [] or [ownName], set accepts [] or a bounded array containing only that name (duplicates may normalize). Successful set returns null only after durable commit; errors reject. Preference is a request, never an execution grant.

Reuse the existing permissioned PluginData transport and TaskRun for `startup.get` (0 args) / `startup.set` (one list arg), backed by per-plugin storage key `__atools_background_startup_v1`. Existing data session bindings still authorize each call. Source detection recognizes this exact legacy IPC use so an original preload can get the normal Data approval before initialization. Data methods cannot start a session or infer background approval. Plugin uninstall removes stored own data by existing lifecycle.

Background execution uses a dedicated `PermissionScope::PluginBackground`, serialized `plugin_background`, a private per-plugin start tool (that scope) and stop tool (empty scopes, trusted matching live owner only, confirmed cleanup). Saved grant or one-time approval goes through the existing capability/TaskRun pipeline; conservative policy never treats the preference or Data grant as consent. The start/stop private source is `plugin_background`. No new HTTP server or Node launcher.

## Native protocol (camelCase DTOs)

- `list_plugin_background_candidates`: trusted main window only; installed, enabled, platform-supported, requested plugins, stable deterministic order, at most128. Returns `{pluginId, pluginName, codeRevision, action}`; action is a trusted empty boot descriptor: original URL/preload/manifest permissions/providers/path, feature_code empty, payload null, auto_detach false. No synthetic Feature activation or history capture.
- `run_plugin_background({requestId,sessionId,pluginId,codeRevision,operation:"start"|"stop"})`: registers an opaque window-owned intent before await, calls the private tool through shared pipeline; returns `{runId,tool,status,permission_required?}` with the native-generated tool ID. Persist exactly these five input fields, never a renderer-provided action. Do not hold any pipeline-owned plugin execution gate clone while waiting for renderer operations which themselves acquire that gate.
- Event `plugin-background-dispatch`, targeted to owning main window: `{requestId,ticket,sessionId,operation,pluginId,codeRevision,action}`. Start action is the current boot descriptor. Stop reuses the existing admission. Start success requires actual loader/document/preload ready; stop success requires awaited panel/runtime cleanup, not unmount scheduling.

`requestId`, `sessionId`, and `ticket` use canonical lowercase UUID strings (36 characters). `codeRevision` is 64 hexadecimal characters. The nested native `FeatureAction` retains its existing snake_case fields. Before sending frame `plugin-enter`, the trusted panel converts that action to public `{code,type,payload,from}` semantics; the original frame never guesses `feature_code` from a boot descriptor.
- `complete_plugin_background({requestId,ticket,sessionId,outcome:"ready"|"closed"|"failed"})`: validates exact live intent/window/ticket/op/binding, one receipt. Pipeline owns terminal TaskRun status. No paths, URLs, payload, bearer endpoints or image bytes in TaskRun input/output.
- `set_plugin_background_waiting({requestId,ticket,waiting})`: pauses only execution deadline during existing nested permission waits. Bounded startup deadline5s / stop5s of active work; pending consent/admission TTL5min, no idle polling or automatic retry storm.
- `cancel_plugin_background({requestId})`: closes only current owned intent and cancels its pending/running TaskRun/permission request. A lost caller cannot strand a pending admission.
- `verify_plugin_background_session({sessionId,pluginId,codeRevision})`: read-only main-window check before cached promotion; returns `{valid:boolean}` (ordinary stale admission is false; foreign owner is rejected). Requires a successful ready admission, current package binding, requested/enabled plugin and no revoked/denied permission. A one-time approval remains valid for that live admission; explicit revocation invalidates it. Never reuse across plugin/installation/revision/document ownership changes.
- `close_plugin_background_session({sessionId})`: idempotent owner-scoped safety teardown/cancellation when renderer is destroyed or normal stop cannot be dispatched. No permission required to release resources. Lifecycle invalidation emits `plugin-background-invalidated` with `{pluginId: string|null}`; closes/cancels exact owners, not unrelated plugins.

Integrate private admission, bind_run, executor routing, cancellation, private-memory/snapshot exclusions, plugin grant revocation/reset, window destroy and app Exit. Runtime never spawns Node: existing PluginPanel loaders and legacy_runtime own that resource. Keep startup TaskRun bounded to readiness; it does not run for the entire resident lifetime.

Successful TaskRun output is `{runtime:"plugin-background",operation,outcome:"ready"|"closed",sessionId,pluginId,codeRevision}` with `initiator.clientId="atools-ui"` and `capabilityId=result.tool`. Subscribe to task-run updates before invoking; once the run ID is known, reconcile its state once and thereafter use events, without a new polling interval during consent.

## Session and performance policy

Maximum2 resident background sessions globally/main window; initial startup attempts at most2, one serialized attempt at a time. No automatic respawn after explicit kill, denial or failure; next application launch can retry a persisted request. All roots still obey existing global Node limit4. MainPush remains transient and separate; before foreground creation release/await unrelated transient query runners, retaining the selected runner while it is being promoted. No per-plugin idle interval.

One admitted plugin document/runtime stays mounted across foreground entry and return to search. Pool keys include plugin identity and trusted code revision/installation descriptor, never feature/payload. A cached foreground activation revalidates native admission, waits for loader ready, then sends the exact owner-validated FeatureAction; it never remounts/reexecutes preload. A pending background intent superseded by a separate foreground cold open must be cancelled rather than create a duplicate instance. Nonresident/ordinary foreground plugins keep their existing lifecycle and do not require background permission.

Persistent `sessionId` is a canonical UUID. Pass it through the pool, panel, loader, and runtime preload to the Node environment as the optional fifth argument (after the existing wait argument); Node instance ID then equals that UUID. Native emergency cleanup may close only exact owner `window:main:<sessionId>` and the matching plugin. Data/Clipboard controllers have their own IDs; await their actual IPC closures and never assume those IDs equal the Node session. Swallowed controller errors cannot produce a successful closed receipt.

Separate immutable document owner from changing visible FeatureAction. Loader/source/Node owner and document generation stay stable across same-document entries; action-specific subinput/list/UI state and pending local permission requests reset. Do not clear source registry or Node capabilities merely because feature code changes. On code update/disable/uninstall/revocation, invalidate all matching hidden and foreground instances, then use normal destroy/reload paths.

Persistent hide uses a distinct authenticated host lifecycle event `plugin-hide`, not the existing terminal `plugin-out` event used by bridge cleanup listeners. It delivers public `onPluginOut(false)` via `atools-plugin-hidden`; resources and Enter subscriptions survive. Real destroy emits existing plugin-out(true), closes all resources and workers, and removes source/IPC state. `outPlugin()` / boolean overload must map to close/hide (`true` kills); keep prior array/object output overload for ATools builtin compatibility. Public callbacks are unchanged original plugin code.

New authenticated lifecycle is `{__atools_lifecycle__:true,event:"plugin-enter",action,activationId}`. Activation IDs are positive safe integers increasing from1 per document; reject invalid or `<=last` IDs using one bounded scalar. Bridge normalizes action, cancels stale selected-feature operations, and invokes the selected Feature export or generic Enter. Existing `featureExports.start` remains initial/idempotent; a separate reentry method handles later true activations. Pagehide/kill disables captured methods. Hide is `{__atools_lifecycle__:true,event:"plugin-hide"}`. Hide is not an authority reset or a security sandbox; plugin-scoped authorized background work is intentional.

Hidden panel does not autofocus, intercept global editing keys or replace the active panel instance. Node/data/clipboard permission waits are observed via existing tracking, not bypassed. Await strict Node close and resource teardown before reporting closed; cleanup failure cannot be reported as success. Foreground promotion uses the actual registered document identity/transport, not a plugin-writable global.
